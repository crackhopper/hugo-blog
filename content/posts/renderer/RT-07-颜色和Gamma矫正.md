# Gamma矫正
## 为什么要做Gamma矫正？
- **人眼的特性（非线性）：** 人眼对暗部细节非常敏感，对亮部细节相对迟钝。如果亮度物理上增加一倍，人眼并不会觉得亮了一倍。
- **显示器的特性（非线性）：** 早期的 CRT 显示器（以及现在的 LCD/OLED 模拟它的特性）输入一个电压信号，发出的亮度和电压不是正比关系，而是呈指数曲线下降的，这个指数就是 $\gamma$（通常是 2.2）。

显示器会把画面**压暗**（右下角的实线），所以我们必须在图像显示之前，提前把画面**调亮**（左上角的虚线），两者一抵消，最后呈现在人眼里的就是完美的线性变化（中间的虚线）。

![[RT-07-颜色和Gamma矫正-为什么要做gamma矫正-01.png]]

## 公式
要把颜色通道的值（红色、绿色、蓝色）缩放到 $[0, 1]$ 之间。

- **编码/校正（把线性渲染好的图像变亮，准备输出到显示器）：**
    
    $$V_{out} = V_{in}^{(1 / \gamma)}$$
    
    _通常 $\gamma = 2.2$，所以指数大约是 $1 / 2.2 \approx 0.45$。_
    
- **解码（把输入的图片恢复成物理线性光，用于图形计算）：**
    
    $$V_{out} = V_{in}^{\gamma}$$
## 代码层面
在着色器（Shader，如 GLSL/HLSL）中，通常在片元着色器的最后一步执行：
```glsl
void main() {
    // 1. 这里是你的光照和颜色计算（在线性空间中进行）
    vec3 linearColor = calculateLighting(); 
    
    // 2. 进行 Gamma 矫正 (指数为 1.0 / 2.2)
    vec3 gammaCorrectedColor = pow(linearColor, vec3(1.0 / 2.2));
    
    // 3. 输出给显示器
    FragColor = vec4(gammaCorrectedColor, 1.0);
}
```

**现代更省事的做法：** 现代图形 API（如 OpenGL, DirectX, Vulkan）支持 **sRGB 帧缓冲区（Frame Buffer）**。你只需要开启它，GPU 会在硬件层面自动在最后一刻帮你做这个 `pow(color, 1/2.2)` 的计算，不需要你在 Shader 里手动写。

## 工作流规范
### 输入时：解码（Remove Gamma）

当你把一张普通的图片（如 `.jpg`, `.png` 的纹理）贴到 3D 模型上时：

- **如果是色彩纹理（如漫反射贴图 Albedo/Diffuse）：** 它们在艺术家制作并保存时，就已经被贴心地施加了 Gamma 矫正。导入引擎计算前，**必须先做反向矫正**（计算 $V^{\gamma}$），把它们打回原形变成“线性颜色”。 （同样，如果纹理放入了sRGB的硬件格式中，反矫正也被自动做了）
- **如果是数据纹理（如法线贴图 Normal, 粗糙度 Roughness, 金属度 Metallic）：** 这些图片里的数值代表的是物理方向或纯数学参数，不是给人眼看的颜色。**绝对不能做任何 Gamma 处理**，直接当做线性数据读取。

### 计算时：保持线性（Linear Calculation）

在 Shader 里面计算物理光照（如 PBR 渲染、各种叠加混合）时，老老实实在线性空间下计算。


### 输出时：编码矫正（Apply Gamma）

当所有的光照、阴影、后期特效全部计算完毕，准备把最终的像素颜色塞给显示器屏幕的前一刻。

- **时机：** 全局渲染流程的**最后一步**。
- **操作：** 执行 $V^{(1/\gamma)}$，或者直接输出到硬件的 sRGB 渲染目标上。


## 测试Gamma矫正是否正确
### 步骤 1：制作测试纹理
你需要准备或在代码中生成两张材质贴图（或者在屏幕上并排画两个正方形）：
- **A 区域（参考组 - 棋盘格）：** 用一个像素黑、一个像素白交替的微型棋盘格填充。无论在什么 Gamma 空间下，它的物理发光总量都是物理世界里的 50%。 （不管是否矫正，模糊看的颜色都是 0.5）
- **B 区域（实验组 - 纯灰色塊）：** 填充一个在线性空间下数值刚好为 `0.5`（即 `vec3(0.5, 0.5, 0.5)`）的纯色。

### 步骤 2：在你的渲染器中对比观察
把 A 和 B 两个区域并排显示在你的程序窗口里。退后三米，或者眯起眼睛，让黑白棋盘格糊成一片灰色。
- **正确的结果：** A 区域（棋盘格）和 B 区域（灰色塊）的**亮度完全一致**，它们融合在了一起，看不出边界。
- **错误的结果：** 两个区域有明显的明暗差。

### 症状一： B 区域（纯色）明显比 A 区域（棋盘格）暗很多
这是最常见的翻车现场。

- **原因：** 你在线性空间里算了 `0.5` 的亮度，但**忘记在输出时做 Gamma 矫正了**。导致 `0.5` 的电压直接输入给了显示器，被显示器物理压暗成了 $0.5^{2.2} \approx 0.21$ 的亮度。
    
- **检查代码：** * 检查屏幕最后一刻有没有写 `pow(color, 1.0/2.2)`。
    
    - 如果用的是 sRGB Framebuffer，检查是否漏掉了 `glEnable(GL_FRAMEBUFFER_SRGB);`（OpenGL）或对应的激活指令。

### 症状二：B 区域（纯色）明显比 A 区域（棋盘格）亮很多
- **原因：** 你做了**两次 Gamma 矫正**（Over-correction）。
- **检查代码：** * 你可能既在 Shader 里手写了 `pow(color, 1.0/2.2)`，同时又开启了硬件的 sRGB 帧缓冲区。赶紧把 Shader 里的手动计算删掉。


# HDR相关处理 (色调映射, Tone Mapping)
如果说 **Gamma 矫正是为了解决“显示器扭曲了色彩”** 的历史包袱，那么 **HDR 则是为了解决“显示器亮度上限太低”** 的物理物理瓶颈。

## 原理
在过去，显示器很弱（SDR/LDR），最暗是 0（纯黑），最亮是 1（通常只有 100 nits 的亮度）。 这导致了一个大问题：**太阳的亮度和一根蜡烛的亮度，在游戏里都被强行卡死在了 `1.0`**。这就叫“过曝”或“白死（Clipping）”，高光细节全丢了。

真实世界的亮度范围是极度夸张的（从星光的 $10^{-5}$ nits 到太阳的 $10^9$ nits）。

- **HDR 渲染：** 让引擎在计算时放开 `0.0 ~ 1.0` 的限制。太阳的亮度可以是 `10000.0`，蜡烛是 `1.0`，电脑屏幕上的反光是 `5.0`。
- **物理突破：** 现代 HDR 显示器（如 MiniLED 或 OLED）的峰值亮度可以达到 1000 nits 甚至 2000 nits 以上，能够真正拉开“蜡烛”与“太阳”的物理亮度差距。

## 步骤概要
在 HDR 工作流中，有两个至关重要的数学步骤：**Tone Mapping（色调映射）** 和 **OETF（光电转换函数）**。

### 核心步骤 A：Tone Mapping（色调映射）

虽然引擎内部数据可以到 `10000.0`，但如果直接丢给显示器，超过 `1.0` 的部分还是会被硬生生裁切掉。

我们必须用一个数学公式，把 `[0, 正无穷]` 的数值，**平滑地压缩** 到一个可控范围内。

- **最简单的公式（Reinhard 算法）：**
    
    $$V_{out} = \frac{V_{in}}{V_{in} + 1.0}$$
    
    _当 $V_{in} = 0.5$ 时，$V_{out} = 0.33$；当 $V_{in} = 10000.0$ 时，$V_{out} \approx 0.9999$。永远不会超过 1.0！_
    
- **电影级公式（ACES 曲线）：** 现代游戏和电影标配。它不仅压缩高光，还能保持中间色调的对比度，并在高光处产生自然的“白里透黄/透红”的物理消散效果。



### 核心步骤 B：色彩空间编码（取代 Gamma 2.2）

传统的 Gamma 2.2 曲线是为 100 nits 亮度设计的，完全不够 HDR 用。HDR 引入了全新的数学曲线：

- **PQ 曲线（Perceptual Quantizer / ST.2084）：** 绝对亮度曲线。它用精确的数学公式把 `0 ~ 10000 nits` 的物理亮度映射到 $[0, 1]$ 的数字区间内。

## ACES 曲线
**ACES（Academy Color Encoding System，学院色彩编码系统）**，是由美国电影艺术与科学学院（就是评奥斯卡奖的那个机构）主导开发的一套**全球通用色彩管理和交换标准**。

在游戏和 3D 渲染里，我们常说的“ACES 曲线”，特指其色彩管线中的核心步骤——**ACES Filmic Tone Mapping（ACES 电影级色调映射曲线）**。

它是现代 3D 引擎（Unreal 5、Unity HDRP、Blender Cycle、电影特效渲染器）的**默认标配**。

### 出发点
在 ACES 普及之前，图形学常用的是 **Reinhard** 曲线（公式为 $\frac{x}{x+1}$）。Reinhard 虽然能把无限亮压缩到 1.0，但它有一个致命的审美缺陷：**高光偏色与不自然的饱和度**。


**传统曲线的痛点（Reinhard）**

当一个物体的颜色非常纯（比如纯高饱和度的红色 `(10.0, 0.0, 0.0)`），随着光照强度不断加大：

- **理想情况（现实物理）：** 强光照射下，物体应该**逐渐泛白**，最终过曝成纯白。
- **Reinhard 的结果：** 它会把绿色和蓝色通道死死卡在 0，只把红色通道往 1.0 挤。结果就是，高光处呈现出一种极度诡异、刺眼的**高饱和度霓虹红**，非常廉价、有“塑料数码感”。

**ACES 的降维打击**

ACES 模拟了传统胶片（Filmic）对光线的物理化学反应。

- **高光去饱和（Desaturation）：** 当光照强度极高时，ACES 会让 R、G、B 三个通道共同向 1.0 靠拢。
    
- **视觉效果：** 纯红色的物体在强光下，核心会自然地**向黄色、白色过渡**（就像火焰中心发白、红铁烧透了发白一样）。这种高光自带一种高贵、厚重的电影质感。

### ACES 曲线的数学结构（五大区间）
如果你把 ACES 曲线画成一张图，它呈现出一条优雅的 **S 型曲线**。这条 S 曲线在数学上被硬生生拆成了 5 个部分，每个部分都在各司其职：
1. **黑电平剪切（Black Clip）：** 过滤掉极微弱的噪声，定义什么是“绝对纯黑”。
2. **暗部（Toe，鞋尖）：** 曲线的最下方。它将暗部细节变平缓，让阴影呈现出胶片般的**深邃感**，黑得下去，又带有微微的细节。
3. **中间调（Linear Region）：** 曲线的中段，几乎是一条直线。确保人眼最敏感的日常亮度范围内，画面对比度绝对自然。
4. **亮部（Shoulder，肩膀）：** 曲线的最上方。在这里，高光开始**弯曲、平缓**地接近 1.0。
5. **白电平剪切（White Clip）：** 定义多大的亮度在屏幕上直接映射为 100% 的纯白（比如大于 10.0 的物理亮度统一归为纯白）。

常用的公式：

对于输入的任何一个颜色通道数值 $x$：

$$f(x) = \frac{x \cdot (2.51 \cdot x + 0.03)}{x \cdot (2.43 \cdot x + 0.59) + 0.14}$$

最后需要将输出结果硬裁剪（Clamp）到 $[0.0, 1.0]$ 区间内。

### 代码
```glsl
vec3 ACESFilm(vec3 x) {
    return clamp((x * (2.51 * x + 0.03)) / (x * (2.43 * x + 0.59) + 0.14), 0.0, 1.0);
}
```
## PQ曲线
### 概念
传统的 Gamma 2.2 曲线是一个**相对亮度曲线**。不管你的显示器上限是 100 nits 还是 500 nits，代码里的 `1.0` 就代表“显示器的最大亮度”。

而 **PQ 曲线（Perceptual Quantizer，感知量化器）**，是一个**绝对亮度曲线**。
- 它是由杜比（Dolby）提出，后来被标准化为 **SMPTE ST 2084**。
- 它的范围被死死锚定在 **$0 \sim 10000$ nits** 的绝对物理亮度上。
- 在 PQ 编码下，数字信号的每一个值，都严格对应一个真实的物理亮度（流明）。例如：数字信号 `0.508` 在 PQ 曲线下，代表的**永远是精确的 100 nits 物理亮度**，无论在什么屏幕上都一样。

### PQ 的数学公式

将物理亮度 $Y$（单位：nits，范围 $0 \sim 10000$）编码为 PQ 信号 $N$（范围 $0 \sim 1.0$）：

$$N = \left( \frac{c_1 + c_2 \cdot Y^{m_1}}{1 + c_3 \cdot Y^{m_1}} \right)^{m_2}$$

_其中 $m_1, m_2, c_1, c_2, c_3$ 都是一堆为了完美拟合人眼视觉特征而算出来的固定常数。_
- **常量 $m_1$ 公式**
    
    $$m_1 = \frac{2610}{16384} = 0.1593017578125$$
    
- **常量 $m_2$ 公式**
    
    $$m_2 = \frac{2523}{256} = 9.85546875$$
    
- **常量 $c_1$ 公式**
    
    $$c_1 = \frac{3424}{4096} = 0.8359375$$
    
- **常量 $c_2$ 公式**
    
    $$c_2 = \frac{2413}{128} = 18.8515625$$
    
- **常量 $c_3$ 公式**
    
    $$c_3 = \frac{2392}{128} = 18.6875$$

### 代码实现

```glsl
vec3 OETF_ST2084(vec3 linearColor) {
    vec3 m_color = linearColor / 10000.0; // 归一化到 PQ 内部空间
    
    float m1 = 2610.0 / 16384.0;
    float m2 = 2523.0 / 32.0;
    float c1 = 3424.0 / 4096.0;
    float c2 = 2413.0 / 4096.0;
    float c3 = 2392.0 / 4096.0;

    vec3 cp = pow(m_color, vec3(m1));
    vec3 num = c1 + c2 * cp;
    vec3 den = 1.0 + c3 * cp;
    return pow(num / den, vec3(m2));
}
```

## ACES和PQ曲线配合问题
### 简单做法
ACES输入如果是1，那么不适合作为 PQ 曲线的输入。真实  ACES 的输出，应该调整到显示器最高支持的亮度。假设是 1400，那么需要调整到 1400。一个最简单的做法如下：

```glsl
// 1. 标准 PQ 编码公式：接受 0 ~ 10000 范围的物理 nits
vec3 OETF_ST2084(vec3 linearColor) {
    vec3 m_color = linearColor / 10000.0; // 归一化到 PQ 内部空间
    
    float m1 = 2610.0 / 16384.0;
    float m2 = 2523.0 / 32.0;
    float c1 = 3424.0 / 4096.0;
    float c2 = 2413.0 / 4096.0;
    float c3 = 2392.0 / 4096.0;

    vec3 cp = pow(m_color, vec3(m1));
    vec3 num = c1 + c2 * cp;
    vec3 den = 1.0 + c3 * cp;
    return pow(num / den, vec3(m2));
}

// 2. 基础 ACES 拟合
vec3 ACESFilm(vec3 x) {
    return clamp((x * (2.51 * x + 0.03)) / (x * (2.43 * x + 0.59) + 0.14), 0.0, 1.0);
}

void main() {
    // 引擎算出来的超亮原始光照
    vec3 rawHdr = calculatePBR(); 
    
    // 【关键步 A】：用 ACES 压缩高光，得到 0 ~ 1 之间的相对比例
    vec3 acesMapped = ACESFilm(rawHdr); 
    
    // 【关键步 B】：根据当前用户的 HDR 显示器能力，放大到物理亮度
    // 假设用户在游戏菜单里设置了显示器峰值亮度为 1400 nits
    float displayMaxNits = 1400.0; 
    vec3 physicalNitsColor = acesMapped * displayMaxNits; 
    
    // 【关键步 C】：用 PQ 曲线对这个真实的 nits 颜色进行打包编码
    vec3 finalPQCode = OETF_ST2084(physicalNitsColor);
    
    // 输出给 Windows HDR 帧缓冲区 (通常是 RGBA16F 或 RGB10A2 格式)
    FragColor = vec4(finalPQCode, 1.0);
}
```

因为PQ编码的，会在显示器被PQ解码。然后按照显示器能显示的范围进行截断。
### 改进做法 HDR ODT
上面写的这段代码，被称为 **"SDR-to-HDR 桥接法"**。它的优点是简单直观，但它有一个小小的缺陷：**它是拿原本为了 100 nits 规划的 ACES 曲线，强行等比例放大到了 1400 nits。** 这会导致中间调（人脸、风景等日常亮度）也被一起等比例放大了，画面整体可能会显得有些过亮、晃眼。

真正的 3D 游戏大作（如 Unreal 5 的 Lumen 渲染器），为了追求极致的电影质感，会采用 **“高动态直接映射”**。

基础版的 ACES 曲线之所以把最大值卡在 `1.0`，是因为 SDR 显示器的上限被焊死了。 但在 HDR_ODT 中，曲线的输出直接代表**物理 nits**。它的数学曲线形态需要发生以下三个根本性改变：

1. **中间调（Linear Region）保持不变：** 真实世界里 10 nits 的凝聚微光、100 nits 的室内面部照明，在 HDR 屏幕上依然应该是 10 nits 和 100 nits。**HDR 绝对不能把原本不亮的东西强行放大。**
    
2. **高光肩膀（Shoulder）无限延展：** 曲线的截止点不再是 `1.0`，而是向右、向上延伸。根据显示器的不同，它可以延伸到 `1000`、`1400` 甚至 `10000`。
    
3. **动态适应（Dynamic Tail）：** 理想的 HDR_ODT 应该接受一个参数（如 `displayMaxNits`），这个参数像一把剪刀，动态地决定曲线在高光处从哪一个点开始平滑弯曲。


#### 广义 HDR_ODT 拟合多项式

对于输入的任何一个通道的原始物理能量 $x$：

$$f_{HDR}(x) = \frac{x \cdot (a \cdot x + b)}{x \cdot (c \cdot x + d) + e}$$
为了让它输出物理 nits（最大 10000），这一组常数被重新计算拟合。标准的 **ACES 10000 nits 理想 HDR_ODT** 系数如下：
- $a = 23.4375$
- $b = 1.0$
- $c = 1.0$
- $d = 136.136$
- $e = 0.0$ （在某些高度拟合版本中，微调分母常数以优化黑点）

#### 显示器限制
由于显示器本身有最大的nits限制。所以，ACES直接输出到 10000 nits，会导致较高的nits无法被现实出来。更好的做法是输出到显示器的nits限制附近。

Unreal的做法：提前在离线状态下，针对 500 nits、1000 nits、2000 nits、4000 nits 的显示器，解出了好几组不同的 $a, b, c, d, e$ 系数。 在 Shader 运行时，根据用户传入的 `displayMaxNits`，在这些已知的系数矩阵之间进行**线性插值（lerp）**。

另一个做法：

```glsl
// 真正的工业级自适应 ACES HDR_ODT
// 参数 x: 原始 PBR 能量
// 参数 maxNits: 玩家显示器的最大亮度（如 1400.0）
vec3 ACES_HDR_ODT_Adaptive(vec3 x, float maxNits) {
    // 1. 根据显示器上限，计算一个动态的“高光压缩阈值”
    // 目的是让多项式内部的自变量范围，完美适应目标显示器
    vec3 k = x / (maxNits * 1.2); // 留出 20% 的高光溢出用于平滑弯曲

    // 2. 核心 ACES 拟合多项式系数（此时它作为一个标准的归一化微调器）
    float a = 23.4375;
    float b = 1.0;
    float c = 1.0;
    float d = 136.136;
    
    // 3. 动态弯曲：高光处的曲线会根据 maxNits 的不同，产生不同的弯曲斜率（Shoulder）
    vec3 normalizedMapping = (k * (a * k + b)) / (k * (c * k + d));
    
    // 4. 将归一化的结果，还原到显示器的绝对物理 nits 空间
    // 此时最大值会自动逼近 maxNits，而不是死死卡在 10000，且没有任何硬截断！
    return normalizedMapping * maxNits;
}

void main() {
    vec3 rawHdr = calculatePBR(); 
    
    // 用户显示器的真实上限（菜单可调）
    float displayMaxNits = 1400.0; 
    
    // 【完美执行你的构想】：内部参数调整，直接输出完美契合 1400 屏幕的物理 nits
    // 此时 1400 以上的能量会被优雅地“平滑揉碎”在 1000~1400 之间，而不是被一刀切
    vec3 physicalNits = ACES_HDR_ODT_Adaptive(rawHdr, displayMaxNits);
    
    // 此时的 clamp 仅仅是为了防止浮点数溢出的保险，实际上曲线已经自动适应了
    physicalNits = clamp(physicalNits, vec3(0.0), vec3(displayMaxNits));
    
    // 送入 PQ 编码
    vec3 finalPQCode = OETF_ST2084(physicalNits);
    
    FragColor = vec4(finalPQCode, 1.0);
}
```
## 工作流：HDR 渲染 vs HDR 显示
这里有一个巨大的误区：**很多游戏支持“HDR 渲染”，但并不需要你有“HDR 显示器”。**

### 软件级 HDR（所有屏幕都能享受）
- **输入：** 贴图依然是普通的 LDR。
- **计算：** 开启 **浮点数画布（如 RGBA16F 格式的 Framebuffer）**。光照计算时，灯光强度设为 `10.0`。
- **输出：** 经过 **Tone Mapping** 把画面压回 `0 ~ 1`，最后通过 Gamma 2.2 输出给普通显示器。
- **好处：** 虽然屏幕最亮还是那么亮，但你看到了原本会曝光过度变成死白的云彩细节、火焰细节。

### 硬件级 HDR（需要 HDR 电脑和显示器）
- **前几步相同**，但在最后一步，**不进行**限制在 `1.0` 的 Tone Mapping。
- 渲染器直接将高动态数据（如 RGBA16F）交给操作系统（Windows 的 HDR 模式）。
- 通过 **PQ(ST.2084)** 曲线编码送给 HDR 屏幕，屏幕的 MiniLED 背光会瞬间飚到 1000 nits，亮瞎你的眼。

## 如何验证与测试 HDR 是否正确？
### 实验 1：超高强度光源测试法（验证 Tone Mapping 存不存在）

1. 在场景里放一个球体，打一个强度为 `100.0`（极亮）的聚光灯。
    
2. 观察球体最亮的核心区域。
    
    - **错误（未做 Tone Mapping 或做错）：** 球体中心是一块极其生硬、边缘像刀切一样的**纯白色色块**。
        
    - **正确（开启了 ACES Tone Mapping）：** 球体中心虽然很亮，但从高光到外围有一层非常平滑、自然的**色彩渐变消散（Roll-off）**，甚至能看到球体贴图本身的纹理细节。

### 实验 2：色彩倾向测试法（验证色彩空间是否崩坏）

1. 将一个物体的颜色设为**纯高饱和度颜色**（例如纯红 `vec3(10.0, 0.0, 0.0)` 或纯黄）。
    
2. 不断加大环境光的强度。
    
    - **错误（没处理好 HDR）：** 随着光照变强，纯红色在屏幕上会变成一种非常诡异、刺眼的**霓虹恶俗红**，甚至变成带有噪点的怪异颜色。
        
    - **正确（标准的 ACES 工作流）：** 随着光照增强，纯红色会自然地向“白里透红”过渡，就像现实中红色的铁块被烧得通红发白一样（这在图形学里叫 Desaturation 高 zealous 饱和度去饱和）。
### 实验 3：硬件 HDR 纯黑/纯白测试

如果是在开发真 HDR（输出给 HDR 显示器）的游戏：

- 在全黑场景里放一个 1000 nits 的白色方块，用亮度计（或肉眼）观察。如果开启 HDR 后，黑色的背景依然在发灰发亮，说明你的黑电平（Black Level）映射错了；如果白色方块和普通白色没有区别，说明你的 PQ 曲线编码没对上 Windows 的 HDR 接口。
